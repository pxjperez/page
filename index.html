Lineamientos de Desarrollo de Software

Principios y prácticas para construir software mantenible, seguro, probado y preparado para evolucionar.

1. Principios generales

Calidad desde el inicio

Diseñar pensando en mantenibilidad, legibilidad y pruebas. Corregir la causa raíz, no solo el síntoma.

Simplicidad

Preferir soluciones claras y pequeñas. Evitar abstracciones prematuras y dependencias innecesarias.

Automatización

Automatizar compilación, pruebas, análisis estático y despliegues repetibles.

Responsabilidad

Todo cambio debe ser trazable, revisable y contar con un responsable técnico.

2. Arquitectura y diseño

  • Separar responsabilidades entre presentación, dominio y acceso a datos.
  • Definir contratos claros entre módulos y APIs.
  • Aplicar principios SOLID cuando aporten claridad y mantenibilidad.
  • Registrar decisiones arquitectónicas relevantes mediante ADR.
  • Evitar acoplamiento directo con proveedores externos cuando sea razonable encapsularlos.

3. Estándares de código

  • Nombres descriptivos para clases, métodos, variables y endpoints.
  • Métodos pequeños, con una responsabilidad predominante.
  • No incluir secretos, contraseñas, tokens ni credenciales en el repositorio.
  • Usar formateadores y linters del lenguaje de forma automática.
  • Eliminar código muerto y comentarios que repitan lo evidente.
  • Manejar errores de forma explícita y registrar información útil sin exponer datos sensibles.

4. Control de versiones con Git

Trabajar mediante ramas y Pull Requests. Mantener cambios pequeños y fáciles de revisar.

Convención sugerida de commits

feat: funcionalidad · fix: corrección · docs: documentación · refactor: refactorización · test: pruebas · chore: mantenimiento

Ejemplo: feat: agregar autenticación de usuarios

Pull Request

  • Explicar qué cambia, por qué y cómo probarlo.
  • Vincular issue o requerimiento cuando exista.
  • Exigir revisión de código antes de integrar cambios.
  • No integrar una rama con pruebas obligatorias fallidas.

5. Pruebas y calidad

  • Crear pruebas unitarias para reglas de negocio y componentes críticos.
  • Usar pruebas de integración para bases de datos, APIs y servicios externos relevantes.
  • Incluir casos positivos, límites y escenarios de error.
  • Ejecutar la suite automatizada en cada Pull Request.
  • Priorizar cobertura útil sobre una cifra de cobertura sin contexto.

6. Seguridad

  • Validar entradas y aplicar controles de autorización en el servidor.
  • Gestionar secretos mediante variables de entorno o un gestor de secretos.
  • Mantener dependencias actualizadas y evaluar vulnerabilidades conocidas.
  • Conceder únicamente los permisos necesarios.
  • Proteger información sensible tanto en tránsito como en almacenamiento según el riesgo y los requisitos del sistema.

7. Integración y despliegue

  1. Instalar dependencias desde archivos de bloqueo cuando estén disponibles.
  2. Ejecutar lint y análisis estático.
  3. Ejecutar pruebas automatizadas.
  4. Construir un artefacto reproducible.
  5. Desplegar por entornos con configuración externa al código.
  6. Contar con observabilidad y una estrategia de reversión.

8. Documentación

Cada repositorio debe incluir un README con propósito, requisitos, instalación, configuración, ejecución, pruebas y proceso de contribución. Las APIs deben documentar sus contratos, códigos de respuesta y mecanismos de autenticación.

9. Checklist antes de integrar

  • ✓ El código compila y pasa los controles automáticos.
  • ✓ Las pruebas relevantes están creadas y pasan correctamente.
  • ✓ No se han añadido secretos ni datos sensibles.
  • ✓ Los cambios fueron revisados.
  • ✓ Se actualizó la documentación afectada.
  • ✓ Se evaluaron compatibilidad, migraciones y plan de reversión cuando corresponda.
